# M8.1.6 — Navigation store UI

## Context

Replace `ui/src/app/features/structures/` with a `ui/src/app/features/navigation/`
feature, following the store-feature pattern (`<feature>.service.ts` typed against
generated OpenAPI schemas + `<feature>.component.ts` signals-based state) and reusing
the shared `sf-tree` component already used for folder trees elsewhere.

## Goals

- `navigation.service.ts`: thin `HttpClient` wrapper over `M8.1.5`'s endpoints,
  `withCredentials: true`, `If-Match` built from `etagFor(revision)` — same shape as
  `channels.service.ts`/`pages` services.
- `navigation.component.ts` + `.html`/`.scss`: tree view (folders + `PageReference`
  leaves) using `sf-tree`; selecting a node opens a detail drawer:
  - Folder detail: rename, `startNode` picker (constrained to that folder's direct
    children per `M8.1.2`'s validation), delete.
  - `PageReference` detail: target picker (searchable Page or page-folder select, kind
    toggle), optional label override, live-resolved "→ /actual/page/path" preview via
    `GET .../resolve`, delete.
- Root folder is shown and behaves like any other folder node (rename disabled, delete
  disabled — matching how the Page/Media store roots are special-cased in the existing
  tree UI, if they are; otherwise match whatever root convention those stores use).
- Route registration under the project shell (mirrors how `structures` was routed) and
  a nav-rail entry replacing the old "Structures" link with "Navigation".

## Acceptance criteria

- [x] Tree renders the full navigation folder structure with `PageReference` leaves,
      matching `GET .../navigation/tree`.
- [ ] Creating/renaming/moving/deleting folders and references works end-to-end against
      the real API (manual verification via `npm run dev`/`ng serve` + backend, not
      just unit tests). **Not verified against a live stack in this environment** — see
      Notes below. Implemented and type-checked against the real `M8.1.5` contract, and
      exercised by the component-test suite (blocked from actually running — see Notes),
      but nobody clicked through a running UI.
- [x] `startNode` picker only offers valid direct children and reflects `null` as "no
      entry page" clearly in the UI (the `<select>`'s first option is literally
      "— No entry page (grouping only) —", and its options are the selected folder's own
      `children` from the already-loaded tree, nothing else).
- [x] `PageReference` detail shows the live-resolved target path, updating when the
      target changes (`GET .../resolve` is called on load and again after every
      successful `PATCH`).
- [ ] Vitest component tests for tree rendering and the two detail-drawer forms — written
      (4 spec files, 13 tests) but **not confirmed green**: `npm run test` is currently
      blocked for every `templateUrl`-based component in this repo by a pre-existing,
      repo-wide test-infra defect, reproduced identically on an unmodified checkout. See
      Notes — left unchecked deliberately rather than claiming a passing suite I could not
      observe.

## Out of scope

- URL registry settings panel (`M8.2.5`).

## Notes / hazards

- Confirm the shared `sf-tree` component supports heterogeneous node types (folder vs.
  reference) with distinct icons/actions before assuming it can be reused as-is.

### Resolution notes (M8.1.6 implementation)

**OpenAPI schema was stale and had to be regenerated first.** `ui/src/app/core/api/generated/schema.d.ts`
had none of `M8.1.5`'s navigation types. Ran `./gradlew :server:sf-app:generateOpenApi`
(writes `server/sf-app/build/openapi/openapi.json`, a build artifact, not committed — same
as `M8.1.5` left it) then `npm run generate:api` from `ui/`, which regenerated
`schema.d.ts` with `NavTreeView`, `NavigationFolderView`, `NavigationStartNodeView`,
`PageReferenceView`, `CreatePageReferenceRequest`, `UpdatePageReferenceRequest`, and
`PageReferenceResolveView`, plus the five new paths under `.../navigation/...`. That
regenerated `schema.d.ts` is committed as part of this task (frontend build depends on it
and it can't be regenerated by `npm run build` itself).

**`sf-tree` finding (per this file's own hazard note):** `ui/src/app/shared/components/sf-tree.component.ts`
is **not** a functional tree — its entire template is `<ng-content />` (a bare
content-projection shell, see `sf-tree.component.html`). It carries no node model, no
icon/type dispatch, and is not referenced anywhere else in the codebase (`grep -rn
"sf-tree"` turns up only its own definition). Every other store tree in this codebase
(`sf-folder-node` for pages, `sf-media-folder-node`/`media-library.component` for media)
builds its own recursive per-feature node component instead of using `sf-tree` for
anything beyond a wrapper `<div>`. Followed the same convention: `nav-tree-node.component.ts`
is a new recursive component (mirrors `folder-node.component.ts`'s shape — expand/collapse,
selection, native HTML5 drag-move) that renders both `NavTreeView.type` values (`FOLDER`
and `PAGE_REFERENCE`) with distinct icons (`folder`/`folder_open` vs `link`) and a
resolved-path chip on reference leaves; `<sf-tree>` is still used as the outer wrapper in
`navigation.component.html` for visual/structural consistency with wherever it's used
elsewhere, but does none of the rendering work itself.

**Final structure**, all under `ui/src/app/features/navigation/`:
- `navigation.service.ts` — thin, self-contained `HttpClient` wrapper (own `etagFor`,
  matching `templates.service.ts`'s/`channels.service.ts`'s shape rather than routing
  through the monolithic `ApiClient`), covering the full `M8.1.5` endpoint table: the
  generic `/folders` CRUD scoped to `NAVIGATION` (create/rename/move/delete — unchanged
  generic endpoints per `M8.1.5`'s own resolution notes), plus the navigation-specific
  `PATCH .../navigation/folders/{uuid}` (raw-body partial update — `startNode` is only
  included in the JSON body when the caller explicitly passes it, via `'startNode' in
  patch`, so "leave untouched" vs. "clear" stays distinguishable exactly as the backend
  requires), `PageReference` CRUD, `resolve`, and a `moveReference` helper over the
  generic `/assets/{uuid}/move` endpoint (a `PageReference` is a normal asset, so its move
  goes through the generic asset-move endpoint, not a navigation-specific one — there
  isn't one).
- `nav-tree-node.component.ts/.html/.scss` — the recursive tree renderer described above.
- `nav-folder-detail.component.ts/.html/.scss` — rename, `startNode` `<select>` (options
  built from the `children` input, which the parent derives from the already-loaded tree
  data — no extra fetch, per this task's Goals), delete.
- `nav-reference-detail.component.ts/.html/.scss` — target kind toggle (`PAGE`/`FOLDER`),
  a `Page` picker via the existing shared `sf-asset-picker-dialog` (`allowedTypes:
  ['PAGE']` — it already supports this out of the box), a flat indented `<select>` for the
  `FOLDER` kind (built from `ApiClient.listFolders(projectKey, 'PAGES', 10)` — reused as-is
  since `sf-asset-picker-dialog` itself has no "pick a folder as the target" mode, only
  "pick an asset while browsing folders"), label override, and the live-resolved preview.
- `navigation.component.ts/.html/.scss` — the container: loads `NavigationService.tree()`,
  owns `selectedUuid`/tree-derived `selectedNode`, fetches the selected node's full detail
  via the generic `ApiClient.assetDetail` (there is no dedicated "get one navigation
  folder" or "get one reference" read endpoint — `M8.1.5` only added mutating/resolving
  endpoints, so the generic asset-detail endpoint, which already returns the full JSON
  `payload`, is genuinely the only way to read a single node's current `startNode`/
  `target`/`label` — confirmed this is not a missing-endpoint gap by re-reading `M8.1.5`'s
  endpoint table), and branches the drawer on `AssetDetailView.type`.
- `index.ts` — barrel export, matching the `channels`/`media` feature convention.

**Root-folder restriction approach:** the navigation root (the tree's top-level node) is
rendered exactly like any other folder node — same icon, same expand/collapse — but
`nav-tree-node` refuses to make it a drag source (`isRoot` guards `dragstart`), and
`nav-folder-detail` hides its rename-edit button and its whole delete-folder footer button
when `isRoot` is true, leaving only its `startNode` picker (still genuinely useful: the
root's own `startNode` is what makes the top of the nav tree itself clickable) editable.
This mirrors the media store's "All media" root, which restricts its own folder actions to
"new subfolder" only (`media-library.component.ts`'s `onRootContextMenu`) — the pages
store has no equivalent restriction because it has no eager root at all (per `M8.1.2`'s
own resolution notes, Pages/Media never got one; only Navigation did).

**Route + nav-rail:** `ui/src/app/app.routes.ts` gained a `navigation` child route under
the project shell, alongside `pages`/`media`/`templates` (component-only, no nested
routes — the drawer is in-component state, not a route). `ui/src/app/features/dashboard/nav-rail.component.ts`
gained a "Navigation" entry (icon `account_tree` — the exact icon the old, since-deleted
`structures` entry used, per `git show <pre-M8.1.1-commit>^:.../nav-rail.component.ts`)
in the same slot the old "Structures" entry occupied, between Media and Templates.

**Old `structures.component.ts`/`.service.ts` (read for UI-convention research per this
task's instructions, not reused as code):** confirmed via `git log --all --diff-filter=D`
+ `git show <commit>^:...` that the old feature was a flat list-with-detail-panel over a
CDL/OCTL-based grammar (`kind: NAVIGATION | BREADCRUMB | LIST`, raw `sourceText`/
`channelTemplates` editing) — structurally unrelated to the new folder-tree-based
navigation store, so nothing was ported directly. The one transferable convention: a
feature-local `*.service.ts` with its own `etagFor` helper (mirrored here) rather than
routing everything through the shared `ApiClient`.

**Build:** `cd ui && npm run build` is green (`ng build`, no new errors; the three
pre-existing SCSS budget warnings on `templates`/`channels`/`media` are unrelated and
predate this change).

**Tests — written but currently blocked from running, and this is a pre-existing,
repo-wide defect, not a defect in this task's code.** Wrote four Vitest/`@testing-library/angular`
spec files (`nav-tree-node.component.spec.ts`, `nav-folder-detail.component.spec.ts`,
`nav-reference-detail.component.spec.ts`, `navigation.component.spec.ts` — 13 tests total,
covering tree rendering with both node types, rename, the `startNode` picker, root
restriction, the reference target/label form, the live-resolved-path preview including its
unresolved state, and delete). Running `npm run test` (`vitest run`) in this sandbox fails
all of them with `Component 'X' is not resolved: templateUrl: ...`. **Reproduced this
identical failure on a clean, unmodified checkout** (`git stash -u` + `npm run test`):
two pre-existing spec files unrelated to this task —
`sf-diff.component.spec.ts` and `sf-empty-state.component.spec.ts` — fail with the exact
same error, so this is not something introduced here. Root cause traced: `ui/vitest.config.ts`
never registers the `@analogjs/vite-plugin-angular` Vite plugin (needed to inline
`templateUrl`/`styleUrl` at transform time so Angular's JIT compiler never needs to
runtime-fetch template resources in `jsdom`), and neither does the `@analogjs/vitest-angular:test`
builder wired up in `angular.json` (its implementation, `src/lib/builders/test/vitest.impl.js`,
calls `startVitest` with no `viteConfig`/plugins argument at all — only the heavier,
unused `build-test` builder target does that). Attempted the documented fix (add
`plugins: [angular()]` from `@analogjs/vite-plugin-angular` to `vitest.config.ts`,
renamed to `.mts` to satisfy its ESM-only import in this CJS-default package): it failed
to even load the config — `@analogjs/vite-plugin-angular@1.22.5` (the version pinned in
the **committed** `package-lock.json`) imports `defaultClientConditions` from `vite`,
which the installed `vite@5.4.21` doesn't export. That version pairing is baked into the
committed lockfile, not a local install drift, so this is a genuine pre-existing
dependency-compatibility gap in the repo's test toolchain, not something in scope to fix
under a UI-feature task (it needs a `vite`/`@analogjs/*` version bump and a full
re-verification of the existing suite). Reverted the `vitest.config.ts` experiment fully
(no net change there) rather than leave a half-working speculative fix in place. Manual
read-through of all four spec files against the final component implementations found no
logic mismatches (assertions match the actual DOM structure, service call signatures, and
`If-Match` etag values the components produce).

**Manual verification against a live stack: not performed, honestly.** No browser or
UI-automation tool is available to this agent in this sandbox to click through a running
`ng serve` + backend stack, so the acceptance criterion's "not just unit tests" bar
genuinely wasn't met here. What *was* done instead: the backend's OpenAPI document was
freshly regenerated and round-tripped through `npm run generate:api` (proving the service
layer's request/response shapes match the real, currently-deployed API contract exactly,
not a stale or guessed one), and `M8.1.5`'s own integration tests
(`NavigationApiIntegrationTest`) already cover the same endpoints this UI calls end-to-end
at the HTTP layer. This is a real gap against the acceptance criterion, flagged honestly
rather than claimed done.
