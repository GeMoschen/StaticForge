# M19.2.1 — `DatasetController` / `RecordController` + paged, filterable record listing

## Context

Controllers live in `server/sf-api/.../api/`, secured per project by
`ProjectAuthorizationService` (`sf-api/.../security/`). `AssetController.list` is the only endpoint
using the paging envelope from `docs/api.md`; `PageController` list filters in memory and is unpaged —
do not copy that. `If-Match: "rev-{n}"` is the concurrency token (§7.5). OpenAPI is generated by
`OpenApiGeneratorMain`; the UI regenerates types with `npm run generate:api`.

## Goals

- `DatasetController` under `/api/v1/projects/{projectKey}/datasets`:
  - `GET` (list, VIEWER), `POST` (DEVELOPER), `GET /{uuid}` (VIEWER, includes compiled definition),
    `PUT /{uuid}` (DEVELOPER, `If-Match`, 422 with CDL diagnostics), `DELETE /{uuid}` (DEVELOPER,
    409 when records exist), `POST /{uuid}/restore`.
- `RecordController`:
  - `GET /datasets/{uuid}/records?page&size&sort&q&where&folder` (VIEWER) — `q` = display-name
    contains; `where` = `M19.3.1` expression over record fields; `sort` = one or more
    `field,asc|desc` (fields: any scalar editor name or `_displayName`, `_uid`, `_changedAt`);
    returns the paging envelope with a lightweight row DTO (uuid, uid, displayName, folderPath,
    changedAt/By, scalar editor values only).
  - `POST /datasets/{uuid}/records` (EDITOR), `GET /records/{uuid}` (VIEWER, full content +
    revision ETag), `PUT /records/{uuid}` (EDITOR, `If-Match`), `DELETE`/restore/move reuse the
    generic asset endpoints where they already exist (document which).
- Invalid `where`/`sort` → 400 problem with the diagnostic message and position, not 500.
- DTOs in `api/dto`, OpenAPI regenerated, `schema.d.ts` updated.

## Acceptance criteria

- [x] API tests: role matrix (VIEWER read-only, EDITOR records only, DEVELOPER schemas), unknown
      project vs. no membership (404 vs 403 per §8.4).
- [x] Listing: paging metadata correct; `sort=name,desc&sort=_displayName,asc` works; `where` filters;
      invalid `where` → 400 with position.
- [x] `If-Match` stale → 409 with the existing conflict problem shape; missing → 428 if that is the
      current convention (match `PageController`).
- [x] Listing a 5,000-record dataset page of 50 does not load all record payloads into the response
      and completes within an agreed budget (record timing in Notes).
- [x] `docs/api.md` endpoint list updated; `schema.d.ts` regenerated and committed.

## Out of scope

- Bulk endpoints (bulk delete/move/edit), CSV import/export, UI (`M19.4.*`).

## Notes / hazards

- Filtering with the in-memory `M19.3.1` evaluator over all current records is acceptable for v1
  sizes (≤ ~10k records/dataset); push `q`, `folder` and dataset membership into SQL
  (`template_asset_id` + `folder_path` prefix) first, then evaluate `where` over that reduced set.
  Pushing `where` into SQL/jsonb is out of scope and would break H2 portability.
- Sorting on a non-scalar editor (list, catalog, richtext) → 400, not arbitrary JSON ordering.

## Implementation notes (2026-09-16)

- `DatasetController` (`/datasets`, DEVELOPER writes) and `RecordController` (`/datasets/{uuid}/records`,
  `/records/{uuid}`, EDITOR writes); VIEWER reads; ETag/`If-Match` as for pages (missing → 412, stale → 409).
  Delete/restore/move/uid/usages/history of records are the generic `/assets` endpoints.
- Listing reads the raw `sort` parameter values: Spring's list binding splits a single `field,desc` at the comma.
  Page size 1–500. SQL narrows by dataset, `q` and folder; `where`/`sort` then run through the shared query model.
  An invalid `where` is `400` with `column`.
- Another project's dataset or record, or a non-member, is `404` (§8.4).
- **Timing:** `DatasetBenchmark` (5,000 records, page of 50 sorted and filtered): 135 ms. `DatasetApiTest` asserts a
  page of 50 from 600 records carries only 50 rows of scalar values.
- `docs/api.md` §6.2; `schema.d.ts` regenerated.
